# 问卦结果 URL 状态化 · Design

**Status:** Draft — pending review  
**Date:** 2026-06-01  
**Scope:** 让用户从结果页（主要是 AI 结果）点击「深入此卦」后，能够深度阅读卦象内容，然后通过浏览器返回或页面按钮，自然回到**带完整结果的首页**，结果不丢失。  
**Depends on:**

- 当前已有的 localStorage 持久化机制（`lib/persist-consult.ts`）
- `useStreamingConsult` hook 的结果结构（`MatchData` + `interpretation`）
- 现有的 `AiResultCard` 组件

---

## 1. 用户拍板的设计决策

| #   | 问题                                        | 决策                                                                                                              | 理由                                                                                      |
| --- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Q1  | 结果状态的主要载体应该是什么？              | **URL search params 作为 Primary Source of Truth**，localStorage 仅作为降级和性能优化                             | 浏览器返回天然生效、刷新不丢、同设备可恢复，符合现代 Web 最佳实践（跨设备分享见 §4 限制） |
| Q2  | 用户修改 situation 后，URL 要不要同步更新？ | **不自动同步**。用户主动提交新问卦时才更新 URL                                                                    | 避免 URL 频繁变化导致混乱，也避免用户误以为“改了输入就改了结果”                           |
| Q3  | situation 文本很长，如何处理 URL 长度？     | **混合策略**：优先尝试压缩放入 URL，超过阈值则降级为 `situationHash` + localStorage                               | 平衡可分享性和 URL 可用性                                                                 |
| Q4  | 浏览器返回按钮的期望行为是什么？            | **直接回到带结果的首页**，无需任何额外操作                                                                        | 这是用户最强烈的隐性期望                                                                  |
| Q5  | 是否要把完整 `interpretation` 放进 URL？    | **不放**。URL 只放重建所需的最小信息（hexagram + phase + situation 标识 + 关键元数据），完整文本依赖 localStorage | 避免 URL 过长，同时保护较长的 AI 输出内容                                                 |
| Q6  | 如何处理 URL 状态和 localStorage 的优先级？ | **URL 优先**。如果 URL 能成功解析出有效结果，则忽略 localStorage                                                  | 让“从链接进入”或“刷新页面”的行为更可预期                                                  |
| Q7  | 隐私问题如何处理？                          | MVP 不做特殊处理，但需在文档中明确说明。未来可考虑增加“生成私密分享链接”功能                                      | 当前阶段以解决核心体验问题为主                                                            |
| Q8  | 经典模式是否也要支持 URL 状态？             | **MVP 不做**，仅覆盖 AI 模式                                                                                      | 降低复杂度，先解决最痛的场景                                                              |

---

## 2. 约束

- **必须保护核心阅读心流**：用户从结果页进入详情页研究义理后，返回时不能丢失上下文。
- **URL 长度必须可控**：目标是绝大部分情况下 URL 能在 1500 字符以内。
- **零回归**：不能破坏现有的“记此一卦”、YaoLocator、历史记录等功能。
- **渐进式交付**：允许先只覆盖 AI 模式，经典模式可后续补上。
- **不破坏现有组件边界**：`useStreamingConsult` 应保持相对独立，URL 状态解析最好放在页面层或独立工具层。

---

## 3. 为什么不选择其他方案？

- **纯靠 localStorage + 恢复条**：用户已经明确反馈体验不好（“结果没了”）。
- **全局状态管理（Zustand 等）**：无法解决刷新、直接访问链接、浏览器返回的问题。
- **把卦象详情做成 Modal**：内容量太大（用户已确认），体验会很差。
- **全量把结果塞进 URL**：不可行，`interpretation` 文本过长，且没有必要。

**结论**：URL 状态是目前最能同时满足「自然返回 + 可分享 + 可刷新」的方案。

---

## 4. 核心数据模型

### 推荐的 URL 状态结构（精简版）

建议使用短 key 以控制长度：

- `s`：situation（压缩后）
- `h`：hexagramNumber
- `p`：yaoPosition
- `c`：confidence
- `hash`：situation 的 hash（用于 localStorage 兜底匹配）

**策略**：

- 尽量把 `situation` 压缩后放入 URL。
- 如果压缩后仍过长，则只放 `hash`，完整数据走 localStorage。
- `interpretation` **不放入 URL**，只在 localStorage 中保留。

### ⚠️ URL 自给性与「分享」的真实边界

渲染 `AiResultCard` 需要的不止 `h/p/c`，还包括 `MatchData` 的 `reasoning`、`yaoBrief`、`yaoConfidence`、`runners`（见 `useStreamingConsult.ts` 的 `MatchData` 定义）以及完整 `interpretation`。这些字段**都不进 URL**，只存在于 localStorage。因此：

- **同设备**（刷新 / 浏览器返回 / 同浏览器打开链接）：URL 提供 `hash`，localStorage 命中完整结果 → 完整渲染。✅
- **跨设备 / 清空缓存后打开分享链接**：无 localStorage 命中 → 只能复原卦号与爻位，`reasoning` / `interpretation` 等为空 → **降级视图**。⚠️

**结论**：MVP 的 URL 状态化解决的是「同设备不丢上下文」，**真正的跨设备分享需要 v2 短链接（后端存储完整结果）**。实现时不要假设 URL 自给自足；跨设备打开应明确走降级 UI，而非报错或白屏。

---

## 5. 状态同步策略

推荐采用以下优先级：

1. **URL 可解析出有效结果** → 使用 URL 数据（最高优先级）
2. **URL 无效，但 localStorage 存在最近结果** → 使用 localStorage
3. **两者都无效** → 展示普通首页

**关键规则**：

- 用户主动点击「问卦」提交新结果时 → 立即用新结果更新 URL（使用 `replace`）。
- 用户只是修改输入框内容但未提交 → **不更新 URL**。
- 从 hexagram 详情页返回时，如果 URL 带状态，则直接使用；否则尝试 localStorage。

---

## 6. 风险与缓解措施

| 风险                       | 影响 | 缓解措施                           |
| -------------------------- | ---- | ---------------------------------- |
| URL 过长被截断             | 中   | 采用压缩 + hash 降级策略           |
| 隐私担忧（情境暴露在 URL） | 中   | 文档说明 + 未来提供“私密模式”      |
| 用户修改 situation 后困惑  | 低   | 明确“只有重新问卦才会更新 URL”     |
| 与未来账号系统冲突         | 中   | 设计时预留 `userId` 字段或会话标识 |
| 经典模式支持滞后           | 低   | MVP 明确只做 AI 模式               |

---

## 7. 非目标（Non-Goals）

- 本期不解决经典模式的结果 URL 状态化。
- 本期不做短链接服务（后续可作为独立功能）。
- 本期不解决“多结果管理”（一个用户同时有多个未保存结果）。
- 本期不处理“结果版本冲突”（用户在不同设备修改了同一结果）。

---

## 8. 后续演进方向

- v2：支持生成短链接（后端存储完整结果）
- v3：与账号系统打通，未登录结果可一键转存到云端
- v4：支持在 URL 中携带部分 `interpretation` 用于分享预览
